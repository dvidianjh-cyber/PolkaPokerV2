# PolkaPoker_v2.0.0.2_SPECIFICATION.md - Project Instance

## 1. Project Summary[cite: 3]
* **Name:** Polka Poker v2.0.0.2
* **Description:** A serverless WebRTC Texas Hold'em game where peers connect to an authoritative Host[cite: 1]. This update separates the process of joining a table from sitting at a seat to create a spectator mode, introduces a modal onboarding flow for seating, and upgrades the visual representation of chips to dynamic stacks.
* **Key Features:** 
    * Spectator Mode: Players join via a join code initially, giving them table access as a spectator without enforcing a seat requirement.
    * Integrated Seat Claiming: Clicking an empty seat triggers a centered modal overlay, prompting the user for their name and avatar, assigning them directly to the chosen seat.
    * Dynamic Chip Stacks: Pill graphics are replaced with stacking chip graphics alongside a numerical value, visually capping at a predetermined height to prevent layout disruption.

## 2. Feature Modules[cite: 3]
* **Module A (Net):** Handles `peerHost.js` and `peerClient.js` connections, strict JSON schema validation, and named-handler pub/sub events[cite: 1].
* **Module B (Engine):** Pure logic managing the `state machine`, blind schedules, pot calculations, and dealer rotations[cite: 1].
* **Module C (UI):** DOM-only logic for rendering Grid structures, managing the `100vh` constraint, handling the centered modal overlay, and dynamic chip SVG generation[cite: 1].

## 3. User Stories[cite: 3]
* **Story 1:** As a spectator, I want to enter a join code on the landing page so that I can observe an active game without taking up an active seat.
* **Story 2:** As a new player, I want to click a "Sit Here" seat and see a centered modal overlay[cite: 1], so that I can input my display name and avatar before committing to the game.
* **Story 3:** As a seated player, I want to see growing graphic chip stacks instead of pills, so that I can instantly gauge the size of the pot and active bets.
* **Story 4:** As a host, I want to process seat requests strictly on a first-come-first-served basis, so that race conditions from multiple spectators clicking the same seat are automatically handled without crashing.

## 4. UI/UX Design[cite: 3]
* **Theme & Styling:** High legibility with a four-colour deck option, and accessible UI contrast[cite: 1]. Overlays use a centered modal format with a backdrop blur.
* **Page Layout:** The main application container must be strictly constrained to `100vh` with overflow hidden to prevent any vertical browser scrolling[cite: 2].
* **Component Specifics:** Player hole cards and action buttons (Fold, Call, Raise) must remain inside the table layout directly adjacent to the local player's avatar[cite: 2]. Dynamic chips must implement a maximum visual stack height limit to ensure grid integrity.

## 5. Technical Specifics & Guardrails[cite: 3]
* **Layout & Positioning:** The interface must be achieved exclusively using CSS Grid or Flexbox[cite: 2]. Never use hard-coded pixel offsets for centering elements[cite: 2].
* **Data Integrity:** The Host validates all messages against forged updates[cite: 1]. LocalStorage profile data relies on strict JSON[cite: 3].
* **A11y (Accessibility):** Maintain ARIA tags and ensure UI contrast meets standards[cite: 1].
* **State Management:** The Host is the single source of truth; all DOM components strictly re-sync to the Host state via event buses.

## 6. Boundary Conditions & Edge Cases[cite: 3]
* **Empty States:** Busted players are transitioned to spectators or empty seats[cite: 1]. The game ends natively if only one player remains[cite: 1].
* **Input Limits:** Player names are strictly capped at 12 characters[cite: 1]. Buy-ins require a positive integer[cite: 1]. 
* **Security:** All user inputs must use `textContent` rendering to ensure XSS-safe output[cite: 1].
* **Race Conditions:** Simultaneous seating requests must be securely caught by the Host. The first request is granted; subsequent requests receive a specific "Seat Taken" client error.

## 7. Project-Specific Logic or Data Structures[cite: 3]
* **Logic A:** Game State Machine enforcing transitions: `LOBBY -> WAITING_FOR_DEAL -> PREFLOP -> FLOP -> TURN -> RIVER -> SHOWDOWN -> WAITING_FOR_DEAL`[cite: 1].
* **Dataset A:** Profile Schema validates avatars as either an emoji ID or standard image data[cite: 1].
